# Design: 메인 화면 표현 현대화

## Context

`FrmMain`은 3단 구조다. 왼쪽은 자료 목록과 예배 순서, 가운데는 미리보기, 오른쪽은 송출이다.
가운데와 오른쪽 단은 각각 머리줄, 슬라이드 목록(가사 또는 PPT 썸네일), 조작 줄, 큰 화면으로 이뤄진다.

코드 분석에서 확인한 관련 컨트롤 (구현 전에 CodeGraph로 다시 확인할 것):

| 영역 | 미리보기 | 송출 |
| --- | --- | --- |
| 머리줄 패널 | `panel9` (`PreviewPanelDisplayName`, `btnToLive`, `btnToOutputMoveNext`, `btnToOutput`) | `panel10` (`OutputPanelDisplayName`, `cbGoLive`, `cbOutputClear`, `cbOutputBlack`) |
| 가사 목록 | `flowLayoutPreviewLyrics` (슬라이드마다 RichTextBox) | `flowLayoutOutputLyrics` |
| PPT 썸네일 | `flowLayoutPreviewPowerPoint` (`ImageCanvas`) | `flowLayoutOutputPowerPoint` |
| 조작 줄 | `panel1` (`panel3`, `flowLayoutPanel1`) | `panel2` (`flowLayoutPanel2`, `panel6`) |
| 상태 라벨 | 없음 | `panel8` (`labelBlackScreen`, `labelHideText`, `labelGapItem`) |
| 큰 화면 | `panelPreviewBottom` → `PreviewHolder` → `PreviewScreen` | `panelOutputBottom` → `OutputHolder` → `OutputScreen` |

## Goals / Non-Goals

- Goals: 미리보기와 송출을 한눈에 구분한다. 송출 상태를 색이 아닌 글자로도 알 수 있게 한다. 잘못 누르는 실수를 줄인다.
- Non-Goals: 배치 변경, 조작 방법 변경, 새 UI 프레임워크 도입.

## Decisions

### D1. 색은 한곳에 모은다

색 값을 여러 파일에 흩어 쓰지 않는다. 팔레트를 한 클래스에 상수로 둔다. 위치는 `Global/gfColorsFonts.cs`를 먼저 검토하고, 맞지 않으면 새 파일을 만든다.

| 이름 | 값 | 쓰는 곳 |
| --- | --- | --- |
| PreviewAccent | `#005FB8` | 미리보기 선택 테두리 |
| PreviewTint | `#E5F1FB` | 미리보기 머리줄 바탕 |
| LiveAccent | `#C4500A` | 송출 선택 테두리, 켜진 송출 버튼 |
| LiveTint | `#FDEDE3` | 송출 머리줄 바탕, 송출 중인 목록 줄 |
| NextSlide | `#8A8A8A` | 다음 슬라이드 점선 테두리 |
| Surface | `#FFFFFF` | 목록 바탕 |
| SurfaceAlt | `#F3F3F3` | 창 바탕 |
| TextPrimary | `#1B1B1B` | 본문 글자 |
| TextSecondary | `#5C5C5C` | 보조 글자 |
| OnAccent | `#FFFFFF` | PreviewAccent, LiveAccent 바탕 위의 글자 |
| LiveAccentText | `#A33F00` | LiveTint 바탕 위의 글자 (나가지 않는 현재 슬라이드). LiveAccent는 LiveTint 위에서 대비가 4.1:1이라 글자로 쓰지 않는다. 이 색은 5.6:1이다 |

글자와 바탕의 명도 대비는 4.5:1 이상이어야 한다. 파랑과 주황은 색각 이상이 있어도 구분되도록 명도가 다르다.

PreviewAccent와 LiveAccent는 PPT 썸네일에서는 선택 테두리로, 가사 목록에서는 선택된 슬라이드의 바탕으로 쓴다. 가사 목록에서 연한 바탕(Tint)을 쓰지 않는 이유는 포커스를 가진 목록의 바탕색과 거의 구분되지 않기 때문이다. 그 위의 글자는 OnAccent를 쓴다. OnAccent와 LiveAccent의 대비는 약 4.67:1로 기준을 겨우 넘으므로, LiveAccent를 더 밝게 바꾸면 안 된다.

### D2. 꾸미는 코드는 Designer 파일 밖에 둔다

`FrmMain.Designer.cs`는 Visual Studio 디자이너가 다시 쓰는 파일이고, 원격 저장소의 WPF 작업과 합칠 때 충돌이 가장 나기 쉽다.
그래서 색과 테두리를 적용하는 코드는 새 partial 파일(예: `FrmMain.ModernUi.cs`)에 모으고, 폼이 뜰 때 한 번 호출한다.
Designer 파일은 새 컨트롤을 추가해야 할 때만 고친다.

### D3. 이전 모양으로 되돌리는 설정을 둔다

예배 중에 문제가 생기면 바로 되돌릴 수 있어야 한다. 설정 하나(기본값: 새 모양 사용)를 두고, 끄면 이번 변경이 적용한 색과 테두리가 전혀 적용되지 않게 한다.
설정은 다른 옵션과 같은 곳(`gfDatabase.LoadSavedData`)에서 읽는다. 옵션 대화상자에 항목을 추가하지는 않는다. 레지스트리 값으로만 바꾼다.

- 위치: `HKEY_CURRENT_USER\Software\EasiSlides\options`, 값 이름 `ModernMainUi`
- 값이 없으면 새 모양이다. 값이 0이거나 숫자로 읽을 수 없으면 이전 모양이다. 읽을 수 없는 값일 때 이전 모양으로 가는 것은 의도한 동작이다. 문제가 있을 때 안전한 쪽으로 간다.
- 시작할 때 한 번만 읽는다. 바꾼 뒤에는 앱을 다시 시작해야 한다.

### D4. 동작을 바꾸지 않는다

클릭, 더블클릭, 끌어 놓기, 키 입력 처리 코드는 건드리지 않는다. 목록을 직접 그리도록 바꾸는 작업(4, 5)에서도 선택과 끌어 놓기 동작이 그대로여야 한다.

### D5. 상태 표시는 색에만 의존하지 않는다

켜짐/꺼짐, 송출 중/미리보기, 다음 슬라이드는 색과 함께 글자나 선 모양(실선/점선)으로도 구분한다.

### D6. 사용자가 고른 선택 색이 우선한다

옵션 창의 "Selected Colour / Selected Back"은 가사 목록에서 선택된 슬라이드의 색을 정한다. 새 모양이 이 설정을 무조건 덮어쓰면 옵션 창의 버튼이 아무 효과 없이 남는다.

- 두 값이 **기본값 그대로**(빨간 글자, 노란 바탕)이면 새 모양의 색(미리보기 파랑, 송출 주황)을 쓴다.
- 사용자가 둘 중 하나라도 **바꿨으면** 사용자의 색을 두 단 모두에 그대로 쓴다. 이때 미리보기와 송출의 구분은 머리줄 바탕색과 썸네일 테두리로만 한다.
- 판단은 색을 칠하는 시점에 한다. 옵션 창에서 색을 바꾸면 앱을 다시 시작하지 않아도 반영돼야 한다.

적대적 리뷰(작업 1, 지적 1)에서 나온 결정이다.

알려진 한계: "기본값 그대로"와 "기본값을 일부러 골랐다"를 구분하지 못한다. 새 모양에서 빨간 글자와 노란 바탕을 그대로 쓰고 싶은 사용자는 되돌리기 설정을 꺼야 한다. 또 두 색 중 하나만 바꿔도 두 단의 가사 목록 색 구분이 사라진다. 옵션 창에 설명을 넣는 일은 이번 범위에 넣지 않는다.

### D7. 고대비 테마에서는 새 모양을 적용하지 않는다

Windows 고대비 테마(`SystemInformation.HighContrast`)가 켜져 있으면 되돌리기 설정을 끈 것과 같게 동작한다. 사용자가 고른 접근성 테마를 밝은 색으로 덮지 않기 위해서다.

알려진 한계: 머리줄 색은 시작할 때, 썸네일 테두리는 썸네일을 처음 만들 때, 가사 목록 색은 칠할 때마다 판단한다. 그래서 앱을 실행한 채로 고대비 테마를 켜거나 끄면 세 부분이 서로 다른 모양이 될 수 있다. 테마를 바꾼 뒤에는 앱을 다시 시작해야 한다.

### D8. 미리보기와 송출은 패널 자체로 구분한다

어느 단인지 판단할 때 컨트롤 이름 문자열을 비교하지 않고 패널 참조를 비교한다. 미리보기 패널도 송출 패널도 아니면 새 모양을 적용하지 않는다. 가사 목록의 선택 색은 전역 표에 저장하지 않고 `FrmMain`이 색을 칠하는 함수에 직접 넘긴다.

### D9. "실제로 나가는 중"의 정의와 표시 (작업 2)

송출 단의 현재 슬라이드는 두 상태 중 하나로 표시한다.

- **나가는 중**: 쇼가 진행 중이고, 검은 화면이 꺼져 있고, 간격 항목이 나가는 중이 아니다.
- **나가지 않음**: 그 밖의 모든 경우 (쇼 꺼짐, 검은 화면, 간격 항목).

글자 숨김은 "나가는 중"으로 본다. 배경은 여전히 화면에 나가기 때문이다. 글자 숨김 여부는 상태 줄이 알려 준다.

| 대상 | 나가는 중 | 나가지 않음 |
| --- | --- | --- |
| PPT 썸네일 | LiveAccent 굵은 실선 테두리 (작업 1과 같음) | LiveAccent 가는 실선 테두리 (보이는 굵기가 굵은 테두리의 1/3, 최소 3픽셀) |
| 가사 목록 | LiveAccent 바탕, OnAccent 글자 | LiveTint 바탕, LiveAccentText 글자 |

색만이 아니라 굵기와 채움으로 구분한다 (D5). 가사 목록에서 나가지 않는 슬라이드의 글자를 TextPrimary로 두지 않는 이유는, LiveTint 바탕이 흰 바탕과 거의 구분되지 않아(1.1:1) 글자색까지 같으면 표시가 안 보이기 때문이다 (적대적 리뷰, 작업 2 지적 7).

가사 목록의 표시를 다시 칠할 때는 현재 슬라이드 하나만 표시가 남아야 한다. 이전에 표시했던 칸은 평소 색으로 되돌린다. 내용이 비워진 칸은 칠하지 않는다. 테두리 굵기 속성은 선택된 썸네일만 다시 그리게 한다. 상태가 바뀔 때 모든 썸네일을 다시 그리면 느리고, 이미지가 없는 썸네일은 PowerPoint를 다시 부른다. 사용자가 선택 색을 바꾼 경우(D6)에는 가사 목록의 두 상태가 같은 색이 된다. 그때는 상태 줄과 썸네일 테두리만 구분해 준다.

상태가 바뀌는 모든 시점에 표시를 다시 그린다: 쇼 시작과 종료, 검은 화면 켜기와 끄기, 간격 항목의 시작과 끝, 슬라이드 이동, 항목 교체. 단축키나 리모컨으로 바뀐 경우도 포함한다. 그래서 버튼 상태가 아니라 앱이 가진 실제 상태 값을 기준으로 한다.

### D10. 상태 줄의 내용 (작업 2)

화면 글자는 앱의 다른 글자와 같이 영어로 쓴다. 한글화는 범위 밖이다. 상태 줄은 새 모양에서 항상 보이고, 세 가지를 항상 글자로 적는다.

| 항목 | 평소 | 주의할 상태 |
| --- | --- | --- |
| 쇼 | `Show: OFF` | `Show: ON` |
| 글자 | `Text: shown` | `Text: HIDDEN` |
| 화면 | `Screen: normal` | `Screen: BLACK` |
| 간격 항목 | 표시하지 않음 | `Gap item` |

평소 상태는 TextSecondary, `Show: ON`은 LiveAccent 굵은 글씨, `HIDDEN`과 `BLACK`과 `Gap item`은 TextPrimary 굵은 글씨다. 기존 라벨(`labelBlackScreen`, `labelHideText`, `labelGapItem`)을 다시 쓸 수 있으면 쓰고, 새 컨트롤이 필요하면 Designer 파일이 아니라 `FrmMain.ModernUi.cs`에서 만든다. 이전 모양에서는 상태 줄이 지금과 똑같이 동작해야 한다.

- **좁은 단**: 글자가 다 들어가지 않으면 평소 상태 글자부터 숨긴다. 주의할 상태 글자(`Show: ON`, `Text: HIDDEN`, `Screen: BLACK`, `Gap item`)는 마지막까지 남긴다. 잘린 채로 두지 않는다.
- **실행 중에 고대비 테마를 켠 경우**: 새 상태 줄을 숨겨 기존 라벨이 보이게 한다. 멈춘 상태 줄이 기존 라벨을 가린 채 틀린 글자를 보여 주면 안 된다. 썸네일의 가는 테두리와 점선 표시도 끈다.
- **상태 줄이 기준이다**: 송출 창에서 F9나 F3을 누르면 앱은 검은 화면 버튼과 글자 숨김 버튼의 눌림 상태를 갱신하지 않는다 (기존 동작). 이때 상태 줄은 실제 상태를 보여 주고 버튼 모양은 따라가지 않는다. 버튼의 눌림 상태를 코드로 바꾸면 기존 처리기가 실행되므로 고치지 않는다.

### D11. 토글 버튼의 켜진 모양과 간격 (작업 2)

- 쇼 버튼(`cbGoLive`)이 켜지면 LiveAccent로 채운다.
- 글자 숨김(`cbOutputClear`)과 검은 화면(`cbOutputBlack`)이 켜지면 Surface(흰색)로 채우고 LiveAccent 테두리를 두른다. 쇼 버튼과 같은 색으로 채우지 않는 이유는 "송출 중"과 "화면을 가린 상태"가 같아 보이면 안 되기 때문이다. LiveTint로 채우지 않는 이유는 머리줄 바탕이 LiveTint라 채운 것이 보이지 않기 때문이다.
- 마우스를 올리거나 누르는 동안에도 켜진 버튼의 채움이 사라지면 안 된다.
- 꺼진 버튼은 머리줄 바탕 위에 테두리 없이 놓인다.
- 쇼 버튼과 옆 버튼의 간격은 글자 숨김과 검은 화면 사이 간격의 두 배 이상이다. 창 크기를 바꿔도 유지된다.
- 아이콘은 바꾸지 않는다. 채운 바탕 위에서 아이콘이 보이는지 캡처로 확인한다.

### D12. 다음 슬라이드 표시 (작업 2)

송출 단에서 현재 슬라이드의 바로 다음 슬라이드에 NextSlide 색 점선 테두리를 그린다. 쇼가 꺼져 있어도 그린다. 마지막 슬라이드에서는 그리지 않는다. 미리보기 단에는 그리지 않는다.

- PPT 썸네일: `ImageCanvas`에 다음 슬라이드 표시를 추가한다. `SelectedBorderColor` 등 표시 속성은 값이 바뀌면 스스로 다시 그린다.
- **굵기**: 점선은 현재 슬라이드의 어떤 테두리보다도 가늘어야 한다. 보이는 굵기는 굵은 테두리의 1/5(최소 2픽셀)이고, 선 조각의 길이는 굵기의 4배, 틈은 3배다. 다음 슬라이드가 현재 슬라이드보다 눈에 띄면 안 된다.
- **기준**: 점선은 `CurSlide` 값이 아니라 화면에 선택된 것으로 그려진 썸네일의 바로 다음에 붙인다. 리모컨으로 슬라이드를 넘기면 선택 테두리가 따라가지 않는 경로가 있는데(`Remote_SlideChanged`, 기존 동작), 그때 점선만 앞서가면 "현재 3, 다음 5"처럼 서로 어긋난다 (적대적 리뷰, 작업 2 지적 1).
- **가사 목록에는 넣지 않는다.** 가사 칸(`RichTextBox`)은 틈 없이 붙어 있어 그릴 자리가 칸 위뿐이다. 칸 위에 덧그리면 RichEdit이 스스로 다시 그릴 때 지워지거나 잔상이 남고, 덧씌운 컨트롤은 칸 가장자리의 클릭을 가로챈다.

### D13. 버튼 설명에 단축키를 적는 방법 (작업 3)

- 대상은 미리보기 단과 송출 단의 머리줄과 조작 줄에 있는 아이콘 버튼이다. 툴바와 왼쪽 목록의 버튼은 이번 대상이 아니다.
- 형식은 `기존 설명 (키)`이다. 예: `Black Screen (F9)`. 기존 설명 글자는 바꾸지 않고 뒤에 붙이기만 한다. 설명이 없던 버튼에는 설명을 새로 만들지 않는다.
- **틀린 단축키를 보여 주느니 보여 주지 않는다.** 버튼과 같은 동작을 하는 키가 코드에서 확인될 때만 적는다. 키 처리 코드(`KeyboardActionHandler`, `HookManager`, 메뉴의 `ShortcutKeys`, 폼의 키 처리기)를 근거로 삼고, 근거를 보고서에 적는다.
- 키를 바꿔 주는 설정이 있다 (`Gf.ReMapKeyBoard`, `KeyBoardOption`). 이 설정으로 실제 키가 달라지는 동작은, 지금 설정에서 실제로 먹는 키를 적는다. 그것을 알 수 없으면 그 버튼에는 단축키를 적지 않는다.
- 쇼가 켜졌을 때만 먹는 키와 송출 창에 포커스가 있을 때만 먹는 키는 적지 않는다. 메인 화면에서 언제나 먹는 키만 적는다.
- 버튼과 단축키의 대응은 `FrmMain.ModernUi.cs`의 한 표에 모은다. 새 모양이 꺼져 있으면 설명을 건드리지 않는다.
- 키 이름은 메뉴가 보여 주는 방식으로 적는다 (`KeysConverter`). 조합 키가 `B, Control`처럼 나오면 안 된다.

구현하면서 정한 것 (적대적 리뷰, 작업 3):

- **적는 키는 세 개다**: 검은 화면 F9, 글자 숨김 F3, 쇼 시작 F12. 모두 Output 메뉴의 단축키이고 포커스가 어디 있든 먹는다. "송출로 복사"는 옵션에서 F8 전역 키를 켰을 때만 F8을 적는다.
- **F9, F3과 버튼의 차이를 받아들인다.** 메뉴 키는 실제 상태를 뒤집고, 버튼은 자기 눌림 상태를 따른다. 평소에는 같다. 송출 창에서 F9나 F3을 눌러 버튼의 눌림 상태가 어긋난 뒤(D10)에만 다르고, 그때는 키 쪽이 실제 상태에 맞게 동작한다.
- **전역 키 옵션을 켠 경우**: 옵션 값만 보고 키를 적는다. 전역 키 후킹이 실제로 살아 있는지는 확인하지 않는다. 후킹이 죽으면 설명에 적힌 키가 먹지 않을 수 있는데, 이것은 설명과 무관하게 원래 있는 약점이다.
- **전역 F10 키만 켠 경우**: 검은 화면 버튼에 키를 적지 않는다. F10은 메뉴 줄도 열어서 버튼과 같은 동작이 아니다.
- 방향키, PageUp/PageDown, Z, M, J는 해당 단에 포커스가 있을 때만 먹어서 적지 않는다. F7과 F11은 비슷한 버튼과 동작이 달라서 적지 않는다.

### D14. 찾기 칸의 너비 (작업 3)

- 툴바의 찾기 칸(`Main_QuickFind`)은 툴바에 남는 공간이 있으면 넓어진다. 최소 너비는 지금 너비, 최대 너비는 360픽셀(배율 100% 기준)이다.
- 찾기 칸 오른쪽에 있는 툴바 항목이 가려지거나 넘침 메뉴로 밀려나면 안 된다. 그렇게 될 것 같으면 찾기 칸을 줄인다. 최소 너비에서도 넘치면 지금과 똑같이 동작한다.
- 창 크기가 바뀔 때마다 다시 계산한다. 계산은 `FrmMain.ModernUi.cs`에 두고, 새 모양이 꺼져 있으면 지금 너비 그대로다.
- 찾기 칸의 동작(입력, Enter, 포커스 단축키, 드롭다운)은 바꾸지 않는다.
- 찾기 칸의 목록이 펼쳐져 있는 동안에는 칸을 **넓히지 않는다**. 너비를 바꾸면 목록이 닫히기 때문이다. 목록이 닫힌 뒤에 넓힌다.
- 목록이 펼쳐져 있어도 창이 좁아지면 칸을 **바로 줄인다**. 이때 목록은 닫힌다. 줄이지 않고 기다리면 찾기 칸이 넘침 메뉴로 밀려나면서 목록만 화면에 떠 있게 되고, 앱이 정상으로 닫히지 않는 것을 구현 중에 확인했다. 이전 모양에서는 130픽셀 칸이 들어가는 한 목록이 닫히지 않았으므로, 이 한 가지는 달라진 동작이다.
- 찾기 칸의 `AutoSize`는 건드리지 않는다. 실행 중에 고대비 테마가 켜지면 너비만 원래대로 돌아가고, 꺼지면 다시 넓어진다.
- "창 너비 1600픽셀 이상이면 300픽셀 이상"은 화면 배율 150%까지의 기준이다. 배율 200%에서는 툴바의 다른 항목이 커져서 1600픽셀 창에 그만한 자리가 남지 않는다.

### D15. 예배 순서 목록을 직접 그린다 (작업 4)

대상은 예배 순서 목록(`WorshipListItems`) 하나다. 찬양집 모드의 목록(`PraiseBookItems`)과 왼쪽 위 자료 목록은 건드리지 않는다.

- 새 모양에서만 목록을 직접 그린다 (`OwnerDraw`). 그리는 코드는 `FrmMain.ModernUi.cs`에 둔다. 새 모양이 꺼져 있으면 `OwnerDraw`를 켜지 않는다. 실행 중에 고대비 테마가 켜지면 기본 그리기로 넘긴다 (`DrawDefault`).
- **줄 높이는 바꾸지 않는다.** ListView는 줄마다 높이를 다르게 할 수 없다. 그래서 구분 항목 위에 빈 간격을 두지 않고, 줄 안에서 구분한다.
- **데이터와 조작은 그대로다.** 항목의 글자, 순서, 아이콘, 저장 형식을 바꾸지 않는다. 클릭, Ctrl/Shift 선택, 더블클릭, 끌어서 순서 바꾸기, 우클릭 메뉴, Delete 키, 방향키 이동의 처리기를 건드리지 않는다. 직접 그리기는 화면에 칠하는 것만 바꾼다.
- 글꼴은 목록의 현재 글꼴을 쓴다 (옵션의 미리보기 글자 크기를 따른다). 굵은 글꼴은 목록 글꼴이 바뀔 때만 새로 만들고, 이전 것은 해제한다.

한 줄의 구성은 왼쪽부터 이렇다.

| 부분 | 내용 |
| --- | --- |
| 표시 띠 (4픽셀) | 송출 중이면 LiveAccent, 미리보기 중이면 PreviewAccent, 아니면 없음 |
| 아이콘 | 지금 쓰는 항목 종류 아이콘 그대로 |
| 제목 | 남는 너비에 맞춰 그리고, 넘치면 말줄임표로 끝낸다. 지금 제목 끝에 붙는 `...`은 앱이 글자를 잘라 붙인 것인지 확인하고, 그렇다면 그 처리는 그대로 두고 그려진 글자가 칸을 넘지 않게만 한다 |
| 꼬리표 (오른쪽 정렬, 하나만) | 송출 중이면 `LIVE`, 아니고 미리보기 중이면 `PREVIEW`, 아니면 항목 종류 |

- **구분 항목** (제목이 `■` 또는 `★`로 시작): 굵은 글씨, SurfaceAlt 바탕, 윗변에 가는 선. 꼬리표는 붙이지 않는다.
- **꼬리표 글자**: `LIVE`는 LiveAccentText 굵게, `PREVIEW`는 PreviewAccent, 종류는 TextSecondary. 종류 글자는 영어로 짧게 쓴다 (`PPT`, `Song`, `Bible`, `Text`, `Media`, `Info` 등 앱이 구분하는 종류를 따른다).
- **좁은 목록에서는 종류 꼬리표를 생략한다.** 목록 안쪽 너비가 260픽셀(배율 100% 기준)보다 좁으면 종류 꼬리표를 그리지 않는다. 제목이 먼저다. `LIVE`와 `PREVIEW`는 너비와 관계없이 그린다.
- **바탕**: 송출 중인 줄은 LiveTint, 미리보기 중인 줄은 PreviewTint. 같은 항목이 둘 다이면 송출이 우선이다.
- **선택된 줄**: 지금과 같은 시스템 선택 색으로 칠한다 (포커스가 있을 때와 없을 때 모두 지금 보이는 색). 표시 띠와 꼬리표는 선택된 줄에도 그린다. 선택 색 위에서는 꼬리표 글자를 선택 글자색으로 그려 읽을 수 있게 한다.
- 키보드 포커스 표시(점선 사각형)를 지금처럼 그린다.

구현하면서 정한 것 (작업 4, 적대적 리뷰 포함):

- **글자는 목록이 쓰는 글꼴 핸들과 GDI `DrawText`로 그린다.** `TextRenderer`로 그리면 같은 글꼴인데도 글자가 목록의 원래 글자보다 넓게 나왔다. 지금 방식은 글자의 모양, 위치, 굵기가 원래 그림과 같다.
- **줄마다 화면 밖에서 먼저 그린 뒤 한 번에 옮긴다.** 쇼 도중 송출 줄의 아이콘이 0.6초마다 바뀌는데, 그때 목록이 줄을 먼저 지우고 나서 다시 그리기 때문에 흰 줄이나 제목이 빠진 줄이 한 프레임씩 보였다 (연속 캡처로 확인). 그래서 줄을 메모리 비트맵에 그려 한 번에 옮기고, 목록이 바탕을 지울 때 우리가 다시 칠할 줄은 지우지 않게 한다 (목록 창의 `WM_ERASEBKGND`만 걸러 내는 `NativeWindow`). 목록 컨트롤 자체의 이중 버퍼링(`LVS_EX_DOUBLEBUFFER`)은 쓰지 않는다. 켜면 모든 줄의 글자 모양이 달라졌다.
- **그 대가로 표시가 없는 줄도 원래 그림과 픽셀 단위로 같지는 않다.** 메모리 비트맵에 그린 글자는 가장자리 색 번짐 픽셀의 값이 화면에 바로 그린 것과 1/255씩 다르다 (줄마다 100~450픽셀). 눈으로는 구분되지 않는다. 새 모양이 꺼져 있으면 완전히 같다.
- **구분 항목도 상태 꼬리표(`LIVE`, `OUT`, `PREVIEW`)는 붙인다.** `★★★사도신경★★★`처럼 `★`로 시작하지만 실제로 송출하는 항목이 있다. 종류 꼬리표만 생략한다.
- **송출 줄의 제목은 빨간색이 아니라 TextPrimary다.** LiveTint 위의 빨간 글자는 대비가 부족하다. 확인되지 않아 표시를 붙이지 않은 줄은 앱이 정한 글자색(빨강 포함)을 그대로 쓴다. 그래서 새 표시가 거절된 경우에도 예전 표시는 남는다.
- **선택된 줄에서는 PreviewTint와 LiveTint 바탕이 보이지 않는다.** 줄을 클릭하면 선택과 미리보기가 함께 일어나므로, 미리보기 줄은 보통 선택 색이다. 그때는 표시 띠와 꼬리표가 상태를 알려 준다.
- 구분 항목의 윗선은 TextSecondary로 그린다.
- 목록이 아주 좁으면(배율 100% 기준 약 100픽셀 아래) 꼬리표도 말줄임표로 줄고 제목은 보이지 않는다.

알려진 한계:

- 꼬리표 때문에 제목이 잘린 줄에는 전체 제목 툴팁이 뜨지 않는다. 툴팁은 목록 컨트롤이 칸 전체 너비를 기준으로 판단한다.
- 위로 옮기기 버튼을 쓰면 빨간 글자색이 옮겨지지 않은 줄에 남는다 (원래 있던 버그). 새 모양에서는 바로 옆에 올바른 `OUT`/`LIVE` 줄이 함께 보인다.
- 다른 예배 목록으로 바꾼 뒤 같은 항목이 같은 위치에 있어도 표시하지 않는다 (안전한 쪽).
- 같은 곡이 두 번 들어 있는 목록에서 송출 중인 쪽을 지우면, 앱이 남은 쪽을 송출 줄로 삼고 표시도 그쪽에 붙는다 (앱의 원래 처리).
- 송출 창을 Esc로 닫은 뒤에는 송출 줄에 새 표시가 붙지 않는다. 앱이 그때 항목 정보를 일부만 되돌려 놓기 때문이다. 예전 빨간 글자는 남는다.
- 항목 종류 꼬리표는 목록이 넓을 때만 나온다. 기본 배치에서는 최대화해도 그 너비에 못 미쳐서, 구분선을 옮기지 않으면 보이지 않는다.
- 줄의 표시를 계산할 때마다 줄 객체를 다시 확인한다 (그릴 때 포함). 계산 결과를 따로 저장해 두지 않는다. 항상 지금 상태를 그리기 위해서다.

### D16. 어느 줄이 송출 중이고 미리보기 중인지 (작업 4)

- 송출 단과 미리보기 단에 올라간 항목이 **예배 순서 목록에서 온 것일 때만** 표시한다. 자료 목록에서 바로 올린 항목은 표시하지 않는다.
- 줄은 제목이 아니라 목록 안의 위치로 찾는다 (같은 곡이 두 번 들어 있을 수 있다). 앱이 이 위치를 어떻게 들고 있는지 코드에서 확인하고, 목록을 고친 뒤(순서 바꾸기, 삭제, 추가, 다른 예배 목록으로 전환)에도 맞는지 확인한다.
- **틀린 줄에 표시하느니 표시하지 않는다.** 위치가 범위를 벗어나거나, 그 줄의 항목이 단에 올라간 항목과 다르면 표시하지 않는다.
- **기억해 둔 줄이 목록에서 빠졌으면 다시 찾는다.** 송출 줄을 끌어다 제자리에 놓으면 앱은 그 줄을 복사본으로 바꿔 넣는다. 항목과 위치는 그대로인데 줄 객체만 바뀌므로, 기억해 둔 객체가 더는 목록에 없으면 같은 위치의 줄을 새로 확인해 기억한다. 이 규칙은 **송출 줄에만** 쓴다. 송출 줄에는 앱이 붙인 송출 표시("O")라는 별도의 확인 수단이 있어서, 새로 찾은 줄이 틀릴 수 없다. 미리보기 줄에는 그런 확인 수단이 없으므로 다시 찾지 않고 표시를 떼어 둔다 (다음에 줄을 선택하면 다시 붙는다). 미리보기 줄까지 다시 찾으면, 다른 예배 목록으로 바꿨을 때 같은 위치에 같은 곡이 있으면 그 줄에 `PREVIEW`가 붙는다. 그런데 미리보기 단의 항목은 이전 목록의 서식을 들고 있어서 그 줄과 같다고 할 수 없다 (작업 4 뒤 시험용 목록에서 확인한 결함과, 그 수정에 대한 적대적 리뷰).
- "송출 중"은 D9의 "실제로 나가는 중"이 아니라 "송출 단에 올라가 있음"이다. 쇼가 꺼져 있어도 송출 단에 있는 항목에 `LIVE` 대신 무엇을 적을지: 쇼가 실제로 나가는 중이 아니면 꼬리표를 `OUT`으로 적고 바탕을 칠하지 않는다. 표시 띠는 그린다. 실제로 나가는 중일 때만 `LIVE`와 LiveTint 바탕을 쓴다.
- 단의 항목이 바뀌거나 쇼 상태가 바뀌면 목록을 다시 그린다. 작업 2의 갱신 지점과 0.6초 점검을 함께 쓴다. 다시 그리기는 달라진 줄만 한다.

### D17. 조작 확인의 범위 (작업 4)

이 PC의 예배 목록은 실제 예배 자료다. 그래서 목록을 바꾸는 조작은 실제 앱에서 시험하지 않는다.

- 실제 앱에서 확인하는 것: 그려진 모양, 클릭 선택, 창 크기와 구분선 이동에 따른 다시 그리기, 송출·미리보기 표시의 갱신.
- 실제 앱에서 하지 않는 것: 끌어서 순서 바꾸기, 삭제, 추가, 우클릭 메뉴의 실행. 이들은 직접 그리기를 켠 것과 끈 것의 이벤트가 같다는 것을 별도 시험 프로그램과 코드로 확인한다.

### D18. 아이콘은 Fluent UI System Icons를 앱이 직접 그린다 (작업 9)

지금 상태 (2026-11-17 조사):

- 모든 툴바가 아이콘 자리를 24x24로 정해 두었는데, 그림은 84x100부터 840x859까지 제각각인 PNG를 줄여서 쓴다. 그래서 선 굵기와 여백이 버튼마다 다르고 흐리다.
- 미리보기·송출 단의 버튼과 목록의 종류 아이콘은 `imageListSys` 하나(16x16, 16비트 색, 52장)를 번호로 나눠 쓴다.
- 화면 배율에 맞춰 그림 크기를 바꾸는 코드는 없다 (`SystemAware`).

결정:

- 아이콘은 Microsoft의 **Fluent UI System Icons**를 쓴다 (사용자 결정, 2026-11-17). MIT 라이선스다 (저장소의 LICENSE, "Copyright (c) 2020 Microsoft Corporation", 2026-11-17 확인). Windows 버전과 관계없이 같은 아이콘이 나온다.
- 아이콘 파일은 SVG이고, 확인한 것들은 색 하나로 채운 경로(`<path d="…">`) 하나로 돼 있다. WinForms는 SVG를 읽지 못하므로, **쓸 아이콘의 경로 글자만 소스 파일 하나에 옮겨 두고 앱이 그 경로를 직접 그린다.** 그림 파일이나 글꼴 파일을 앱에 넣지 않는다. 그래서 프로젝트 파일(`*.csproj`)을 고칠 일이 없다.
  - 경로 문법은 SVG 경로 명령(M, L, H, V, C, S, Q, T, A, Z와 소문자 상대 명령)을 읽는 작은 해석기로 처리한다. 쓰기로 한 아이콘에 나오는 명령은 모두 지원해야 하고, 모르는 명령을 만나면 그 아이콘은 실패로 처리한다 (틀린 모양을 그리지 않는다).
  - 아이콘마다 `fill-rule`을 함께 옮긴다. 경로가 여럿인 아이콘은 모두 옮긴다. 색(`#212121`)은 버리고 팔레트 색으로 칠한다.
  - 원본은 크기별로 따로 그려져 있다 (12, 16, 20, 24, 28, 32, 48). 그릴 픽셀 크기보다 크지 않은 것 중 가장 큰 원본을 골라 그 크기에 맞춘다 (16픽셀에는 16, 20픽셀에는 20, 24픽셀에는 24). 필요한 크기만 옮긴다.
  - 보통 모양은 `regular`, 켜진 상태와 강조 쌍은 `filled`를 쓴다.
- 내려받는 것: 쓸 아이콘의 SVG 파일들만 (`https://raw.githubusercontent.com/microsoft/fluentui-system-icons/main/assets/<이름>/SVG/ic_fluent_<이름>_<크기>_<모양>.svg`, 파일 하나가 0.4~3KB, 모두 합쳐 1MB 미만). 작업 폴더(저장소 밖)에 받아 경로 글자를 옮긴 뒤 저장소에는 SVG를 넣지 않는다. 어느 파일에서 왔는지(이름, 크기, 모양, 받은 날짜의 저장소 커밋)를 소스 파일에 적는다.
- 라이선스 고지: 저장소에 `THIRD-PARTY-NOTICES.md`를 두고 MIT 고지 전문을 넣는다. 아이콘 경로를 담은 소스 파일 머리에도 출처와 라이선스를 적는다. 배포본(설치 파일)에 이 고지를 함께 넣는 일은 배포 절차에서 해야 한다 (Known Leftovers).
- 아이콘 하나를 그리지 못하면(해석 실패 등) 그 버튼만 지금 그림을 쓰고 한 번 기록한다. 화면이 뜨는 것을 막지 않는다.
- 검토한 다른 방법: (가) 같은 아이콘의 글꼴 파일(`FluentSystemIcons-*.ttf`)을 앱에 넣는 방법. 수 MB짜리 파일 두 개를 리소스로 넣으려면 프로젝트 파일을 고쳐야 한다. (나) Windows에 들어 있는 아이콘 글꼴(Segoe Fluent Icons). 내려받을 것이 없지만 Windows 10 이전에는 없고 모양이 다르다.
- 그림은 **실제로 쓰이는 픽셀 크기**로 만든다 (툴바의 실제 아이콘 크기, 목록의 실제 아이콘 크기). 만든 뒤에 줄이거나 늘려서 쓰지 않는다. 만든 그림은 모아 두고 화면이 닫힐 때 해제한다.
- 색: 평소는 TextPrimary, 쓸 수 없는 버튼은 시스템이 흐리게 그리는 방식 그대로, LiveAccent로 채운 버튼 위는 OnAccent. 삭제 아이콘도 평소 색이다 (빨강을 쓰지 않는다. 송출 색과 헷갈린다).
- 새 모양이 꺼져 있거나 고대비 테마이면 아이콘을 바꾸지 않는다. 원래 그림(resx)은 지우지 않는다.

`imageListSys`는 번호에 기대는 코드가 많다 (종류 아이콘은 짝수가 보통, 다음 홀수가 강조. 검은 화면 15/16, 글자 숨김 17/18. 상태 줄 12~14). 그래서 **번호 배치가 같은 새 목록**을 만들어 바꿔 끼운다. 바꾸지 않는 번호에는 원래 그림을 그대로 넣는다. 번호를 쓰는 코드는 고치지 않는다.

### D19. 어떤 아이콘을 쓸지는 견본 표로 먼저 확인한다 (작업 9)

틀린 그림이 붙은 버튼은 그림이 없는 버튼보다 나쁘다. 구현 에이전트는 버튼마다 고른 아이콘을 이름, 앱이 그린 그림(쓰이는 크기 그대로와 4배 확대), 지금 그림과 함께 한 장의 표로 만들고, 총괄과 사용자가 그것을 보고 확정한 뒤에 버튼에 붙인다. 아이콘 이름은 기억이 아니라 저장소의 파일 목록으로 확인한다. 앱이 그린 그림이 원본과 같은지도 이 표에서 확인한다 (해석기 검증: 구멍이 있는 모양, 곡선, 여러 조각).

- 종류 아이콘(찬양, PowerPoint, 성경, 메모, 안내 화면, Word, 미디어)은 한눈에 서로 달라야 한다. 강조 쌍은 같은 아이콘의 `filled`를 LiveAccent로 그린다.
- 맞는 아이콘이 없는 버튼(예: 중국어 변환, A/B/C 이동)은 지금 그림이나 글자를 그대로 둔다.
- 미리보기에서 송출로 보내는 버튼들(`btnToOutput`, `btnToOutputMoveNext`, `btnToLive`)과 쇼 버튼(`cbGoLive`)은 예배 중에 가장 많이 누른다. 지금 그림과 뜻이 같아 보이는지 따로 확인한다.

### D20. 툴바의 글자 (작업 8)

- 위쪽 툴바의 편집 버튼(New, Edit, Copy, Move, Delete)과 Media, Refresh, Options에 아이콘과 글자를 함께 보인다. 글자는 지금 설명(툴팁)에 있는 영어 낱말을 쓴다. 나머지는 아이콘만 둔다.
- 창이 좁아 다 들어가지 않으면 순서대로 줄인다: 먼저 찾기 칸을 최소 너비까지 줄이고(D14), 그래도 넘치면 글자를 숨긴다(아이콘만). 그 뒤에도 넘치면 지금과 같이 동작한다. 글자가 보이는 동안 툴바 항목이 넘침 메뉴로 밀려나면 안 된다.
- Delete는 다른 편집 버튼과 구분선 하나만큼 떨어뜨린다.
- 버튼의 순서와 동작은 바꾸지 않는다.

### D21. 글꼴 (작업 10)

메인 화면은 글꼴을 따로 정하지 않아 WinForms의 기본 글꼴을 쓴다. 디자이너에 따로 적힌 글꼴 10곳(MS Sans Serif 7곳, Tahoma 3곳)만 기본 글꼴의 같은 크기와 굵기로 맞춘다. 화면 전체의 글꼴이나 크기는 바꾸지 않는다 (배치가 글꼴 크기에 맞춰져 있다). 가사 칸의 글꼴(옵션에서 정함)은 건드리지 않는다.

### D22. 툴바와 메뉴의 모양 (작업 10)

- 메인 화면의 모든 툴바, 메뉴 줄, 우클릭 메뉴에 같은 그리기 방식(renderer)을 쓴다. 지금은 위쪽 툴바만 그라데이션이고 나머지는 시스템 모양이다.
- 바탕은 SurfaceAlt 한 색, 테두리 선과 그립 없음. 마우스를 올리면 옅은 회색, 누르면 조금 더 진한 회색, 켜진 버튼(CheckOnClick)은 PreviewTint 바탕에 PreviewAccent 가는 테두리.
- 구분선은 가는 선 하나다.
- 상태 줄(`statusStripMain`)의 오류 알림 칸은 지금 색 그대로다.

### D23. 테두리와 바탕 (작업 10)

- 팔레트에 `Border`(`#D1D1D1`)와 `Hover`(`#E9E9E9`), `Pressed`(`#DDDDDD`)를 더한다.
- 입체 테두리(Fixed3D 3곳, RaisedInner 4곳)는 없애거나 Border 색 가는 선으로 바꾼다. 구분선(SplitContainer)을 끌 수 있는 자리는 알아볼 수 있어야 한다.
- 바탕이 `ActiveBorder`(8곳), `ButtonFace`, `Control`로 섞여 있는 패널은 SurfaceAlt로 맞춘다. 뜻이 있는 색(검은 화면 영역의 어두운 바탕, 상태 라벨의 강조색, 미리보기/송출 머리줄의 Tint)은 그대로 둔다. 어느 것이 뜻이 있는 색인지는 구현 전에 목록으로 정리해 총괄에게 확인받는다.
- 컨트롤의 위치와 크기는 바꾸지 않는다. 테두리를 없애 1~2픽셀 달라지는 것은 괜찮다.

### D24. 아래쪽 탭 (작업 10)

탭의 위치(아래쪽)와 순서는 그대로다. 선택된 탭을 PreviewAccent 밑줄(탭이 아래에 있으므로 윗줄)과 굵은 글자로 표시하고, 나머지는 평평하게 그린다. WinForms의 탭 컨트롤은 탭 머리만 직접 그릴 수 있고 바깥 테두리는 바꿀 수 없다. 직접 그린 탭이 시스템 테두리와 어긋나 보이거나 깜빡이면 이 항목은 하지 않고 캡처와 함께 이유를 적는다.

## Known Leftovers

- (작업 9) Fluent UI System Icons의 MIT 고지는 저장소의 `THIRD-PARTY-NOTICES.md`에 둔다. 배포본에 이 파일을 함께 넣는 일은 배포 절차의 몫이다.

- 왼쪽 자료 탭의 PowerPoint 썸네일은 선택 테두리가 빨강 그대로다. 미리보기/송출 구분과 무관하므로 이번 범위에서 고치지 않는다.
- Text / Set / Info 전환 버튼의 눌린 색도 빨강 그대로다.
- 쇼가 꺼져 있어도 송출 단의 현재 슬라이드가 주황으로 표시된다. 작업 2에서 다룬다.
- (작업 2, 2차 리뷰) 송출 단이 아주 좁으면(약 260픽셀 이하) 썸네일이 작아져 가는 테두리와 굵은 테두리가 같은 굵기가 된다. 최소 굵기 3픽셀이 굵은 테두리 전체와 같아지기 때문이다. 이때는 상태 줄만 송출 여부를 알려 준다.
- (작업 2, 2차 리뷰) 송출 단이 상태 글자 하나도 못 담을 만큼 좁으면 주의 상태 글자까지 숨겨진다. 새 상태 줄이 기존 라벨을 덮고 있어서 그때는 검은 화면 표시가 전혀 보이지 않는다. 보통 창 크기에서는 일어나지 않는다.
- (작업 2, 2차 리뷰) 상태 줄 라벨의 여백과 버튼 테두리 굵기는 화면 배율에 따라 커지지 않는다. 쇼 버튼 앞의 간격만 배율을 따른다.
- `HighlightRichTextBox`의 포커스가 없는 쪽 분기는 `GapItemOnDisplay`를 보지 않는다. 그런데 이 값을 참으로 만드는 코드가 없어서 실제로는 차이가 없다. 간격 항목은 `OutputItem.Type == "G"`로 판단한다 (D9). `gfUiText.cs`는 고치지 않는다.
- (해결됨, 작업 2) `ImageCanvas.SelectedBorderColor`가 값을 바꿔도 다시 그리지 않던 것.
- (해결됨) `FormatLyricsContainers`가 슬라이드마다 `Font`를 만들던 문제는 `fix-leftover-resource-cleanup`에서 고쳤다.
- `FormatLyricsContainers`는 미리보기와 송출을 패널 이름 문자열로 구분한다. 이번 변경 이전부터 있던 코드라 그대로 둔다.

## Verification (작업 묶음마다)

1. `dotnet build Easislides\Easislides.csproj -nologo -v minimal`이 오류 없이 끝난다. 이번 변경으로 새 경고가 생기지 않는다.
2. 앱을 실행해 메인 화면을 캡처하고 사양의 시나리오와 눈으로 대조한다. 캡처는 미리보기만 채운 상태와, 미리보기를 송출로 복사한 상태 두 가지를 찍는다.
3. 되돌리기 설정을 끈 상태로도 캡처해 이전 모양과 같은지 본다.
4. 적대적 리뷰와 내장 코드 리뷰의 지적 사항이 모두 처리됐거나, 처리하지 않은 이유가 기록돼 있다.

## Risks / Trade-offs

- **목록 직접 그리기(작업 4, 5)**: 선택, 끌어 놓기, 키보드 이동이 깨질 수 있다. 이 두 작업은 리뷰에서 동작 확인을 따로 요구한다.
- **PPT 항목 캡처**: PPT 항목을 고르면 PowerPoint가 뜬다. 캡처 뒤 PowerPoint 프로세스가 남지 않는지 확인한다.
- **원격과의 충돌**: 원격의 `FrmMain.Events.cs`, `FrmMain.Layout.cs`에 작은 변경이 있다. 작업 7이 `FrmMain.Layout.cs`를 크게 고치므로 합칠 때 충돌할 수 있다.
- **WinForms의 한계**: 둥근 모서리와 부드러운 글자 표현은 시안보다 거칠다. 시안과 똑같이 만드는 것은 목표가 아니다.
