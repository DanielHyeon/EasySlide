# Design — a050 브랜치 전체 코드 리뷰가 찾은 결함

## 현재 구조 (영향 근거)

CodeGraph CLI는 이 세션에서 쓸 수 없었다. 아래는 `/code-review`(2026-11-28)가 코드를 읽어 낸 결과이고 실행으로 확인된 것은 없다. 구현자는 Phase 0에서 항목마다 줄 번호, 부르는 곳, 이미 잡는 예외를 확인한다.

- `CaptionConsole.xaml.cs` 1238줄 근처 `StartWhenUsed`: `obs.json`이 있으면 `ConnectAsync` → `ObsOperator.ConfigureAsync`(설정 창의 값으로 `obs.json`을 다시 씀). `ObsOperator.StartAsync`는 읽기 실패를 잡아 `SettingsReadFailed`만 알린다.
- `CaptionConsole.xaml.cs` 1412줄 근처 `Step`: `async void`, `await _host.StepOutputAsync(direction)`에 try/catch 없음. Axicultus 호스트의 다음·이전 명령이 예외를 스스로 잡는지는 확인되지 않았다.
- `CaptionSession.cs` 369줄 근처 `OnLiveChanged`: `_visible`·`_text`·`Published`를 바꾸고 `PropertyChanged`·`PublishedChanged`를 부른 스레드에서 올린다. `CaptionHost.cs`의 계약 글은 `ICaptionLiveSource.Changed`가 다른 스레드에서 올 수 있다고 한다. Axicultus의 `LiveSessionCaptions`가 실제로 어느 스레드에서 올리는지는 구현자가 확인한다.
- `CaptionDeck.cs` 51줄 근처: 상자 목록은 모든 `p:sp` 자손, 같은 파일의 `AllText`는 `mc:Fallback` 아래와 숨긴 도형·묶음을 뺀다.
- `Axicultus.Core\SongExchangeSequence.cs` 71줄 근처 `IsVerseCodes`, 같은 파일의 `ToLegacy`·`IsTokenText`·`ToDatabase`.
- `Axicultuss\Global\gfLyrics.cs` 3372줄 근처: 순서 글 만들기.
- `Axicultus\Shell\WorshipListStore.cs` 314줄 근처 `RestoreFromTrash`.

## 결정

1. **재현 먼저**: 항목마다 결함을 드러내는 테스트를 먼저 쓰고 고치기 전 코드에서 실패를 확인한다. 실패하지 않으면(결함이 아니면) 그 항목은 고치지 않고 이유를 tasks의 검증 결과에 적는다. 테스트로 만들 수 없는 것(주석)은 검색 결과로 대신한다.
2. **OBS 설정 보존**: `ObsOperator`가 설정 읽기가 끝나지 않았거나 실패했음을 기억한다. 그 상태에서는 운영자가 설정 창에서 직접 연결(또는 저장)을 누르기 전에는 `obs.json`을 쓰지 않는다. `StartWhenUsed`의 자동 연결은 읽기가 성공으로 끝난 뒤에만 한다. 운영자가 직접 누르면 그때의 값이 저장된다(파일을 고칠 기회). a048의 "해독되지 않는 비밀번호는 다시 써서 지키기"와 같은 방향이다.
3. **장 넘기기 실패**: `Step`이 예외를 잡아 자막 탭 상태 줄에 안내하고 `_host.WriteError`로 남긴다. 취소는 조용히 끝낸다. 같은 꼴의 다른 `async void`(자막 탭의 버튼·키 처리기 중 호스트를 기다리는 것)를 찾아 같은 처리가 필요한지 목록으로 보고하고, 호스트 호출을 기다리는 것만 같이 고친다.
4. **라이브 알림의 스레드**: 자막 세션이 만들어진 디스패처로 옮겨 처리한다(이미 그 스레드면 바로). 계약 글은 그대로 둔다(호스트에 부담을 주지 않는다). 옮겨진 뒤 순서가 뒤바뀌지 않게 한다(큐에 넣은 순서대로).
5. **글상자 목록**: `AllText`와 같은 두 거르기를 쓴다(같은 함수로 묶을 수 있으면 묶는다). 상자 키는 바뀌지 않아야 한다(운영자가 저장한 상자 선택이 그대로 맞아야 한다): 키가 바뀌는 PPT가 있는지 테스트로 확인하고, 바뀌면 총괄에게 보고한다.
6. **곡 순서의 구분자**: 탭·CR·LF 말고는 제어 문자가 없고 `IsTokenText`가 참이면 글로 읽는다. `ToDatabase`도 같은 판단을 쓴다. 절 코드로 저장된 기존 값(제어 문자가 섞인 실제 코드 열)이 글로 잘못 읽히지 않는지 반대 방향 테스트를 넣는다.
7. **순서 글의 쉼표**: 모르는 코드는 쉼표째 뺀다.
8. **휴지통 되돌리기**: 한쪽 옮기기가 실패하면 이미 옮긴 쪽을 되돌려 놓고 실패를 알린다. 되돌리기도 실패하면 그 사실을 오류에 담는다(조용히 삼키지 않는다).
9. **주석의 한글**: 브랜치에서 추가된 코드 줄(`git diff origin/main...HEAD`)의 주석에 있는 한글을 영어로 바꾼다. 글자열, 리소스, `.md`, 테스트 자료는 건드리지 않는다. 동작 변경이 없음을 빌드와 전체 테스트로 확인한다.

## 적대적 리뷰 뒤의 결정 (2026-11-28)

10. **곡 순서: 저장된 값을 읽는 규칙은 건드리지 않는다(결정 6을 바꾼다).** 구현자의 좁힌 규칙도 저장된 코드 열의 뜻을 바꾼다. 리뷰어가 길이 5까지의 저장 값 3,368,420개를 모두 비교해 840개가 다르게 읽히고 다르게 다시 쓰이는 것을 실행으로 보였다(9·10·13절이 엔딩 `e`나 프리코러스2 `p` 사이에 있는 값. 예: `e\te`가 "엔딩, 9절, 엔딩"에서 "엔딩, 엔딩"으로). 실제 곡에 있을 가능성은 아주 낮지만, 틀리면 송출 순서가 조용히 바뀌고 다른 DB에서 가져올 때 다시 쓰이며 WinForms와 읽기가 갈린다. 그리고 원래 구멍도 반만 막힌다(앞뒤 끝의 탭·줄바꿈은 여전히 코드로 저장된다).
    - `IsVerseCodes`와 `ToDatabase`는 HEAD로 되돌린다.
    - 글이 들어오는 곳에서 고친다: 교환 파일 가져오기(`ImportExportService.LoadExchange`)와 옛 글 파일 가져오기(`LoadLegacyText`)는 순서 값을 글로 다룬다. 앞뒤를 자르고 탭·CR·LF를 쉼표로 바꾼 뒤 저장 형식으로 바꾼다(교환 파일의 순서는 언제나 글 토큰이다).
    - 다른 곡 DB에서 가져오기(`LoadDatabase`, `LoadAccessDatabase`)는 저장된 코드를 옮기므로 건드리지 않는다(자르면 끝의 9·10·13절이 사라진다).
    - 곡 편집기는 이미 탭과 줄바꿈을 거절한다.
    - 테스트: 가져오기 단계에서(탭, 줄바꿈, 앞뒤 끝의 줄바꿈이 있는 교환 파일과 글 파일), 저장된 코드 열의 읽기·쓰기는 HEAD와 같음.
11. **글상자 목록: 겹친 것만 뺀다(결정 5를 좁힌다).** 숨긴 글상자는 지금처럼 목록에 둔다. 운영자가 자막 전용 글을 숨긴 상자에 넣어 쓰는 경우 그 선택이 말없이 사라지기 때문이다(전체 글은 원래 숨긴 도형을 빼므로 고르지 않은 숨긴 글이 나갈 일은 없다). `mc:Fallback` 아래의 상자는 같은 키의 상자가 이미 목록에 있을 때만 뺀다(대체 내용에만 있는 상자는 남는다). 이름 없는 상자의 번호는 지금과 같다.
12. **보호되지 않은 다른 호스트 호출도 막는다(결정 3을 넓힌다).** `Step`의 `_host.CanStepOutput`, `StagePickedRow`의 `_host.SendPicked()`, `PrepareDeckAsync`의 PPT 읽기(지금은 정해 둔 종류의 예외만 잡는다), `SaveAsync`의 `_recovery.Capture()`. 호스트 예외는 자막 탭에 안내하고 오류 기록에 남기며 디스패처로 나가지 않는다. 쇼가 돌지 않을 때 처리되지 않은 UI 예외는 앱을 끝내기 때문이다(`OperationalErrorLog.OnUiException`은 쇼 중에만, 10초에 5번까지만 삼킨다). 탭이 닫히는 중의 취소는 지금처럼 조용히 끝낸다.
13. **OBS 설정을 읽지 못했을 때의 안내**: 자막 탭의 안내에 "연결을 누르면 지금 설정 창의 값으로 저장된다"는 뜻을 넣는다(운영자가 저장된 값을 덮어쓰게 됨을 알고 누르게). 읽기가 끝나기 전에 만들어진 탭(창이 뜬 직후의 아주 짧은 사이)은 자동 연결하지 않고 같은 안내를 보인다. 읽기를 다시 하는 기능은 넣지 않는다(앱을 다시 켜면 된다).
14. **라이브 알림 순서 테스트**: 다른 스레드의 알림이 줄 서 있는 동안 UI 스레드에서 온 알림이 그 뒤에 처리되는 경우를 테스트에 넣는다.

## `/code-review` 뒤의 결정 (2026-11-28)

15. **고른 항목 올리기는 기다릴 수 있는 일로 바꾼다(호스트 인터페이스 변경).** `ICaptionHost.SendPicked()`가 `void`라서 Axicultus 호스트는 명령을 실행만 하고(`AsyncRelayCommand.Execute`) 실패는 도구 모음의 `async void`를 거쳐 디스패처로 나간다. 자막 탭의 try에 잡히지 않는다. `Task SendPickedAsync()`로 바꾸고 자막 탭이 try 안에서 기다린다(`StepOutputAsync`와 같은 꼴). `PickedSending`이 그대로 필요한지는 구현자가 확인해, 필요 없으면 없앤다. a047의 Axicultuss 호스트는 이 모양으로 구현한다.
16. **세션의 디스패처는 언제나 있다.** 지금은 필드 초기화에서 `Dispatcher.FromThread`로 잡아, WPF 객체가 하나도 없는 스레드(WinForms 호스트)에서 세션을 만들면 null이 되고 스레드 옮기기가 통째로 꺼진다. 세션을 만드는 스레드의 디스패처를 생성자에서 확실히 얻는다(생성자가 어차피 `DispatcherTimer`를 만든다). 디스패처가 없는 스레드라는 경우는 없앤다.
17. **알림 순서는 동시에 와도 지킨다.** "줄 선 것이 없으면 바로 처리"의 판단과 줄 세우기를 한 단위로 묶는다(두 스레드가 거의 동시에 알릴 때 뒤의 것이 먼저 처리되지 않게). 처리 순서는 도착 순서와 같다.
18. **읽는 중에 만들어진 자막 탭**: OBS 설정 읽기가 아직 끝나지 않았을 뿐인데 탭이 "읽지 못함" 상태로 굳고, 안내대로 연결을 누르면 기본값이 저장된 설정을 덮어쓴다. 읽기가 진행 중이면 그 끝을 기다린 뒤 설정 창의 값을 채우고 평소처럼 동작하게 한다(탭 쪽에서 기다리든 앱이 탭을 만들기 전에 기다리든 작은 쪽). 읽기가 실패로 끝난 경우만 결정 13의 안내를 보인다.
19. **OBS 안내는 탭의 상태 줄을 덮지 않는다.** 복구할 것이 있다는 안내와 같은 줄을 다투므로, OBS 안내는 OBS 표시 줄과 설정 창의 상태에만 둔다.
20. **복구 중의 PPT 읽기 실패**도 결정 12와 같게 다룬다(어떤 예외든 PPT 없이 복구를 계속하고 다시 열라는 안내).
21. **Axicultuss의 글 내보내기(.esn)**: `FrmExport`의 순서 글 만들기가 고치기 전의 `ConvertSequenceToTextString`과 같은 꼴이고(쉼표 겹침) 범위 검사도 없다(160 이상의 글자에서 `IndexOutOfRangeException`). 고친 함수를 쓴다.
22. **Axicultuss의 XML 항목 가져오기**(`gfUtility.ExtractAxicultusXMLItem` → `ConvertTextStringToSequence`)도 탭·줄바꿈을 고치지 않는다는 구현자의 관찰: 실제로 잘못 저장되는지 테스트로 확인하고, 그렇다면 결정 10과 같은 고치기를 넣는다.

## 총괄 검증 중에 찾은 것 (2026-11-28)

23. **이번 실행이 스스로 저장한 복구를 "복구할 수 있다"고 안내한다(전부터 있던 결함).** WPF 하네스에서 자막 탭을 처음 열 때 상태 줄이 a048 실행에서는 비어 있었고 이번에는 복구 안내가 보였다. 원인은 a050이 아니다: 자막 탭은 `Loaded`를 두 번 받고(앱 시작 때 접힌 칸에서 한 번, 처음 보일 때 한 번) `LoadRecovery`가 두 번째에도 복구 파일을 다시 읽는다. 새 프로필에서 두 번째 읽기가 찾는 것은 이번 실행이 시작 뒤에 저장한 자기 상태다. 보이는지는 첫 화면 맞춤의 상태 줄 지우기와 몇 ms 차이의 경쟁으로 갈린다(HEAD와 지금 코드의 사건 순서는 같다).
    - 두 번째 읽기를 없애기만 하면 안 된다: 앞선 실행이 남긴 진짜 복구의 안내가 탭을 처음 볼 때 다시 뜨는 길이 그것뿐이다(예배 중 앱이 죽은 뒤 다시 켰을 때 운영자가 복구가 있음을 알아야 한다).
    - 고치기: 이 자막 탭이 복구를 한 번이라도 저장했으면 그 뒤의 `LoadRecovery`는 파일을 다시 읽지 않는다(파일은 이제 이번 실행의 상태다). 앞서 읽어 둔 복구(앞선 실행의 것)가 있으면 그것을 그대로 두고 안내만 다시 보인다. 저장한 적이 없으면 지금처럼 읽는다.
    - 테스트: 새 프로필에서 탭이 스스로 저장한 뒤 처음 보이면 안내 없음·복구 버튼 꺼짐. 앞선 실행의 복구가 있으면 스스로 저장한 뒤에도 처음 보일 때 안내가 보이고 복구는 앞선 실행의 것이다.

## 2차 적대적 리뷰 뒤의 결정 (2026-11-28)

24. **Axicultuss의 순서 글 읽기가 10절 이상을 버린다(전부터 있던 결함, 리뷰어가 실행으로 증명).** `Gf.ConvertTextStringToSequence`가 9보다 큰 절 번호를 버린다. 쓰는 쪽(`ConvertSequenceToTextString`, `FrmExport`)은 `10`, `11`을 쓰고 Axicultuss는 1~99절을 지원하므로(`InitializeVerseHeadings`), 내보냈다 가져오면 10절 이상이 조용히 사라진다(`1,10,11,12,c` → 1절과 후렴만). XML 가져오기, .esn 글 가져오기, 정보 파일 읽기가 모두 이 함수를 거친다. 1~99를 받는다(WPF의 `ToLegacy`와 같게). 테스트: 1~99 왕복, 100 이상과 0·음수는 지금처럼 버림.
25. **결정 15의 테스트를 진짜로**: 지금의 "같은 작업인지" 확인은 고치기 전 코드에서도 통과한다. 실제 호스트(`MainViewModelCaptionHost`)의 올리기가 실패하거나 아직 끝나지 않았을 때를 드러내는 테스트로 바꾼다(명령이 실제로 기다리는 경우: 돌려준 작업이 끝나지 않았고, 실패가 그 작업으로 온다). 제품 코드에 시험용 갈고리를 넣지 않고는 만들 수 없으면 그 사실과 이유를 적고, 통과만 하는 테스트는 지운다.
26. **호스트 계약에 한 줄**: 자막 세션은 UI 스레드(메시지를 돌리는 스레드)에서 만든다. 다른 스레드에서 만들면 다른 스레드의 라이브 알림이 처리되지 않는다.
27. **결정 23의 틈**: 첫 복구 읽기가 끝나기 전에 탭이 스스로 저장하면 그 읽기를 버려, 앞선 실행의 복구가 안내되지 않는다. 탭의 저장은 진행 중인 첫 읽기가 끝난 뒤에 한다.
28. **작은 것**: 고른 항목 올리기가 취소로 끝나면 조용히 끝낸다(장 넘기기와 같게). OBS 설정을 읽지 못한 뒤 운영자의 연결이 성공하면 설정 창의 "읽지 못했다" 안내를 지운다.

## 고치지 않는 것과 근거

- `ImageCanvas.cs` 324줄 근처(`OnPaint` → `RebuildForNewWidth`가 보이는 썸네일을 다시 읽고 높이를 바꿈): 창 크기를 바꿀 때 버벅일 수 있다는 성능 지적이다. 잘못된 결과가 나오는 결함이 아니고, PPT 미리보기 성능 개선(CLAUDE.md 11절 백로그)에서 다룬다.

## 위험과 대응

- **예배 중 경로**: 2·3·4는 자막의 송출 경로다. Axicultus 자막 테스트 전체와 WPF 하네스 `captiontab`·`pptcaption`으로 확인한다.
- **스레드 옮기기**: 지금 UI 스레드에서 바로 처리되던 알림이 늦어지면 자막이 한 박자 늦을 수 있다. 이미 UI 스레드면 바로 처리해 지금 동작을 지킨다.
- **곡 순서**: DB에 저장된 값의 읽기 규칙이다. 기존 코드 열·글 모두에 대한 양방향 테스트로 고정한다. DB는 고쳐 쓰지 않는다.
